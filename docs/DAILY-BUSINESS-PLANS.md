# JR PHEEF daily business plans

The daily business-plan endpoint is implemented in `routes/operations.js`. The GitHub Actions workflow calls it once per day at 05:30 East Africa Time (02:30 UTC), and can also be started manually from GitHub Actions.

## One-time secure setup

The scheduler uses one shared secret. Generate a long random value (at least 32 bytes) and store the same value in both places:

1. **GitHub:** Repository → Settings → Secrets and variables → Actions → New repository secret. Name it `DAILY_PLAN_CRON_SECRET`.
2. **Render:** JR PHEEF web service → Environment → add `DAILY_PLAN_CRON_SECRET` with the exact same value. Save the change and allow the service to redeploy.

Do not commit the secret, put it in this file, or paste it into source code.

Until both values match, the scheduled workflow safely skips when the GitHub secret is absent; if the GitHub secret exists but the Render value is missing or different, the protected endpoint returns 404 and the job fails.

## What gets delivered

- The endpoint selects up to 500 business workspaces where `daily_plan_enabled = true`.
- Each workspace receives at most one saved plan per Africa/Nairobi calendar date.
- A JR PHEEF notification is created for the business owner when a new plan is saved.
- The planner reads completed POS receipts for the business over a bounded rolling 14-day window and compares the latest seven days with the preceding seven days.
- It reads the active product catalogue and configured stock/reorder levels, and can highlight low-stock and out-of-stock products.
- It summarizes sales, receipt counts, average receipt value, units sold and top products. Sales are not profit; the planner does not infer margins, cash balances or customer identities.
- The AI planner receives the same measured snapshot as the safe template fallback. If AI is unavailable, the template still uses measured POS signals where present.
- Each business is queried by its own workspace ID; customer-level data is not supplied to the planner.
- Plans are recommendations. Physical stock counts must be verified. Purchases, price changes, supplier orders and customer contact still require business-owner approval.

## Run manually

After the two secrets are configured, open GitHub Actions → **JR PHEEF daily business plans** → Run workflow. Check the job output for the number of workspaces processed, plans created, reused and failed.

## Data readiness and limitations

The POS-aware planner is implemented and deployed, but it only has useful trading intelligence after a business has entered reliable POS products, completed sales and stock movements. Empty POS tables produce a profile-based plan with an explicit no-POS-data warning; they do not produce invented sales or stock facts.

The current snapshot is limited to completed POS receipts and active product stock/reorder fields. It is not yet a complete accounting ledger: it does not calculate profit, reconcile bank or M-Pesa settlements, model supplier payables, identify customers, or establish KRA/eTIMS compliance. Those require separately validated modules and authorized integrations.

Before relying on automated daily delivery, configure the matching `DAILY_PLAN_CRON_SECRET` in GitHub Actions and Render. Until that is done, plans can still be generated by an authorized member on demand, but the scheduled workflow will not deliver them.
